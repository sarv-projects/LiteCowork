## 1. paradev: the persistent terminal daemon (Feature 008 B-23, capability 3)

LiteCowork's accepted B-23 requires a daemon-owned PTY/ConPTY that survives Workbench tab switches and preserves running child processes. paradev is the reference implementation of exactly this, and it goes further than the spec by surviving app restarts.

- **Out-of-process terminal host.** The terminal is not owned by the renderer or even the main process directly; it is a separate **terminal-host** process the main process talks to through `TerminalHostClient` (`terminal-host/client.ts`, `types.ts`). `DaemonTerminalManager` (`terminal/daemon/daemon-manager.ts`) is the main-process manager that connects to it, so closing or reloading the window never kills a session. `stop-pty-daemons.ts` is the explicit teardown. This is precisely the "the desktop window and the Runtime are separate; closing the UI must not destroy work" principle (capability 17) applied to terminals.
- **Create-or-attach with concurrency control.** Sessions are created or re-attached through a `PrioritySemaphore` (`CREATE_OR_ATTACH_CONCURRENCY`) with a `pendingSessions` map keyed by request id, so concurrent attaches to the same pane coalesce rather than spawn duplicates (`daemon-manager.ts:~55-75`). LiteCowork's terminal service (008-T10) needs this single-flight attach.
- **Cold restore.** `coldRestoreInfo` plus a `HistoryManager` and a bounded `MAX_SCROLLBACK_BYTES` ring let a session be restored with its scrollback after the host or app restarts (`daemon-manager.ts:~64`, `history-manager.ts`). `truncateUtf8ToLastBytes` keeps the tail UTF-8-valid. This is the honest version of "preserve running processes and child processes when changing views."
- **Killed-session tombstones.** `killedSessionTombstones` (bounded `MAX_KILLED_SESSION_TOMBSTONES`) record a pane that was deliberately killed so a late reattach does not silently respawn it (`daemon-manager.ts:~78-95`). This is the same fencing discipline LiteCowork uses for stale leases: a terminal that was stopped stays stopped even under a racing reattach.
- **Deferred cleanup.** `cleanupTimeouts` + `SESSION_CLEANUP_DELAY_MS` keep a session briefly after its pane closes so a quick tab-switch reattaches instead of losing it. `terminal-escape-filter.ts` sanitizes control sequences; `headless-emulator.ts` lets the host run without a renderer.

For LiteCowork: Feature 008's B-23 terminal provider should be an out-of-process host like this, with create-or-attach single-flight, cold restore with bounded scrollback, killed-session tombstones, and deferred cleanup. It maps cleanly onto the accepted "daemon-owned PTY/ConPTY per tab under an admitted Environment, containment receipt, ordered receipts, timeout-as-receipt" (B-23). Proposed task note on 008-T08/T10/T11.

## 2. paradev: the worktree model (Feature 005, capability 3)

paradev's workspace is either a `branch` workspace (works in the main repo path) or a `worktree` workspace (its own Git worktree path), tracked in a local DB (`worktree.ts getWorkspacePath`, `worktrees` table via drizzle). Import flows (`select-external-worktrees-for-import.ts`, `useImportAllWorktrees.ts`), a detached-worktree migration (`branch-detached-worktree.ts`), and status caches (`worktree-status-caches.ts`) round it out. This is the "isolated Git worktrees for coding Tasks by default, explicit in-place when chosen, parallel agents with separate worktrees" requirement (capability 3) with a concrete data model: persist each worktree, resolve a workspace to its path, and treat branch-in-place as a distinct workspace type. LiteCowork's Feature 005 (isolated Task execution) and the coding-cockpit task (008 P-13) should adopt this branch-vs-worktree workspace typing and persisted worktree registry.

## 3. ZCode: atomic directory activation (Feature 013 install, capability 7)

ZCode's plugin installer activates a plugin directory with a crash-safe transaction (`plugins/atomic-directory.ts`): a staged copy is prepared, then renamed into place with a transaction record (`AtomicTransactionRecordV2`: `transactionId`, `ownerId`, `ownerPid`, `mode: coordinated|standalone`, `hadTarget`, `authorityPath`), returning `{finalize, rollback, transactionId}`. A process-owner id and pid let a recovery pass tell its own in-flight transaction from a crashed one, and `activeAtomicReservations`/`activeAtomicTargets` prevent two concurrent activations of the same target. This is the directory-install analogue of DeepSeek's manifest+lockfile rollback and LiteSPM's byte-exact restore: an interrupted install leaves either the old directory or the new one, never a half-written tree. LiteCowork's Feature 013 skill/package install (013-T09) and backup/restore (017) should use this owner-pid transaction-record pattern for crash recovery.

## 4. ZCode: plugin source adapters and UI surfaces (Features 013, 016)

- **Source adapters** (`github-archive-source.ts`, `hook-sources.ts`, `markdown-frontmatter.ts`, `mcp.ts`, `official-marketplace.ts`, `version-compare.ts`) normalize plugins from a GitHub archive, a marketplace, or SKILL.md-style markdown frontmatter into one typed shape, with semver `version-compare`. This corroborates the open-design and DeepSeek finding: the ecosystem norm is to accept SKILL.md / .claude-plugin / archive sources and normalize to one manifest (LiteCowork 013 P-22).
- **`ui-surfaces.ts`** declares the plugin's UI surfaces that the MCP-Apps host mounts. Combined with `UI_PLUGIN.md` (read in full earlier: MCP Apps via `@modelcontextprotocol/ext-apps`, tool-result interactive pages via `_meta.ui.resourceUri`, conversation-side surfaces, reference-selection-back-to-chat, revisioned editable documents, active-page preservation across tab switches, desktop-local-only scope), this is the complete model for LiteCowork capability 13 (Intelligent UI / Interactive Artifacts) and capability 12/co-edit (Feature 012, 016): build interactive artifacts on MCP Apps with typed resources and host-rendered surfaces, make them revisioned editable documents, and support selecting from the artifact back into the conversation.

## 5. The MCP-Apps host fixture (ZCode, capability 13 safety)

ZCode's `packages/desktop/scripts/mcp-apps-host-fixture/` is a battery of host-side checks for managed MCP-App pages: `managed-permission-checks`, `managed-lifecycle-checks`, `managed-model-checks`, `managed-environment`, `guest-evaluation`. It shows the host enforcing a permission and lifecycle contract on a guest page rather than trusting it - the registered-component, restricted-state discipline LiteCowork's 016 requires, with a concrete test surface to model acceptance on.

## 2. Architecture: processes, protocol, IPC

**Three processes plus a Host.** The Electron main process (`src/main.ts`) owns windows, protocol, updater and lifecycle. A **Host** is a child spawned from the same Electron binary in Node mode (`host-process.ts` spawns `process.execPath` with `--expose-internals`, `stdio: ['ignore','pipe','pipe','ipc']`, env built by `node-environment.ts`) running the full product backend (HTTP, WebSocket, agent runtime, plugins). The renderer is a sandboxed `BrowserWindow` loading the product web app.

**The shell is thin by design.** `README.md` "Key technical decisions" table: release identity is one unit (Electron shell, matching dsh runtime, pnpm), the web transport is shared with plain Web mode, plugin changes go through the same HTTP plugin manager as Web. There is no plugin-management IPC and no filesystem or shell access exposed to any renderer **(README, Installation ownership)**.

**Custom scheme, two origins.** `main.ts` registers `dsh-app` as standard, secure, fetch-capable, CORS-enabled, streaming, code-cached (`registerSchemesAsPrivileged`). `protocol.handle` serves `dsh-app://shell/` from packaged static assets with no Host dependency (so update and welcome documents work while the Host is down) and `dsh-app://app/` as: packaged web assets for a fixed allowlist of paths, otherwise a forwarded request to the Host, 503 until the Host and its cookie exist. `web-document.ts` `serveWebDocument` enforces GET/HEAD only, decodes the path, resolves it and refuses any target outside the root (path-containment), and injects a tiny script that creates a `Promise.withResolvers()` boot gate into `index.html` so the page waits for asynchronous Host injections.

**HTTP forwarding.** `forwardWebRequest` rejects a foreign `Origin`, rebuilds headers (dropping `host`, `origin`, `cookie`, `sec-fetch-site`), attaches the Host auth cookie itself, forwards with a streamed body and the request's abort signal, and strips connection-level response headers plus `set-cookie` so the cookie never reaches the page. Plugin bundle responses are rewritten to `no-store` because per-launch revisions would only accumulate in Chromium's disk cache. WebSockets get their `Origin` and cookie rewritten in `session.webRequest.onBeforeSendHeaders` only for the owned window and the Host authority, and cancelled if the origin is not `dsh-app://app` (`main.ts` ~line 700).

**Host IPC protocol.** `host-protocol.ts` carries `DESKTOP_HOST_PROTOCOL_VERSION = 4`. Host to shell events are a closed set validated by a hand-written guard (`isDesktopHostEvent` in `host-process.ts`): `starting{runId uuid}`, `ready{url, injections}`, `fatal{message, diagnostic}`, `platform-session`, `shutdown-complete`, plus correlated control responses `update-tasks`, `quit-inspection`, `file-drag-resource`. An invalid event is a protocol failure: the shell fails and `SIGTERM`s the child. `shutdown-complete` while not stopping is also a failure ("unrequested shutdown"). Shell to Host requests go through one `control()` method with a numeric request id, a per-request deadline (10 s update tasks, 2 s quit inspection, 12 s drag authorization), an `AbortSignal`, and cleanup of the pending map on every path.

**Renderer IPC.** `ipc.ts` holds the closed channel table `DESKTOP_IPC` (35 channels, all `dsh-desktop:`-prefixed) and `assertDesktopSender`, which requires the sender frame URL to be `dsh-app:` on an allowed hostname. `main.ts` `assertProductSender` is stricter: the sender must be the owned main window's `webContents`, the frame must be that window's `mainFrame`, and the URL must be the app origin. Boot, theme, locale, update and keyboard channels each re-check this. Preloads (`preload-app.ts`) use `contextBridge.exposeInMainWorld` only when `location` is the app origin; subframes and shell documents get an empty `dshDesktop`. Shell documents (update dialog, mandatory overlay) get their own isolated preloads and a private `MessageChannel` between preload and frame.

## 3. Agent and session runtime (what the shell knows about it)

The desktop app contains **no agent loop**. It supervises a Host and asks it three questions through the control channel, and the answers drive the entire shell lifecycle.

1. **Admission lock and task inspection for update** (`updateTasks('inspect'|'lock'|'unlock')`, 10 s). "Active" means running agents including subagents and approval waits, queued messages, running or stopping jobs, and (for locking) admitted requests still draining **(README, Updates)**. API reads alone do not count as work. Locking returns 503 for new requests, drains admitted ones, then re-inspects, because an admitted write can create work.
2. **Quit inspection** (`inspectQuit()`, 2 s): `{activeTasks, scheduledTasks}`. Scheduled reminders armed in sessions loaded this run count; unloaded sessions are neither counted nor resumed **(README, Closing the window)**. `quit-confirmation.ts` maps the result to one of three explanations; a failed or late inspection is treated as "running tasks" ("unknown warns", it never quits silently).
3. **File-drag authorization** (`resolveDragResource`, 12 s): the Host confirms a session-scoped resource maps to a local file and returns size and a private digest; the shell checks device, inode, size and times before lending the file to the OS.

Tests prove the Host side separately: `tests/fixtures/host-update-qualification.mjs` boots the real profile loader and checks queued turns/steps, a running model request, pending questions/approvals, global and agent jobs in running/stopping states, admission lock without cancellation, restored admission, and rejected inspection after disposal **(tests/README.md, Evidence)**.

**Additional findings (verified, pass 2).**
- **Close admission, then ask once more.** The `updateTasks` control returns a boolean per mode. `main-startup.spec.ts` pins the sequence `inspect`, `lock`, `unlock` when `lock` reveals work that started during confirmation (the shell then unlocks and refuses with "New tasks"), and `inspect`, `lock` with no unlock when the Host is stopping. An aborted or failed drain also unlocks without stopping the Host.
- **One decision per quit.** `DesktopQuitConfirmation.confirm()` inspects once per decision, joins repeated quit requests to the open prompt (focusing it where the platform allows), and never re-inspects after approval. `dispose()` resolves any pending decision to false so a bypassing quit (session end, installer, development restart) cannot be overtaken by a late "Quit" click. Button order differs by platform (macOS lays out from the right).
- **Session end never waits for a prompt.** Windows `session-end` and macOS `powerMonitor` `shutdown` set a flag that skips the confirmation; a cancelled macOS shutdown clears it on the next focus or show.
- **File-drag authorization is stronger than pass 1 stated.** The Host returns a session-scoped resource's path, size and SHA-256; the shell requires the basename to equal the expected drag filename, `stat` to show a regular file of the declared size, hashes the whole file while streaming, requires device, inode, size, mtime and ctime to be unchanged across the hash, and re-checks them again when the OS drag starts. Preparation requests carry an id of at most 128 characters, are single-use, and can be aborted by id.

## 4. Plugin and extension handling at the desktop layer

The plugin manager itself is covered in A-58. What `apps/desktop` adds:

- **Profile ownership.** Electron exclusively owns `$DSH_HOME/profiles/desktop` and takes the process-lifetime single-instance lock **before any profile access** (`single-instance.ts`, `claimDesktopSingleInstance`; `main.ts` claims before `main()`). CLI and Desktop share user data but never executable packages, lockfiles or `node_modules` **(README, State ownership)**. The installed `dsh plugin --profile desktop` command is allowed only while the app is quit and refuses an uninitialized profile.
- **Core packages are immutable and signed.** Core dsh and the Host live in `app.asar/dsh` with a `desktop-runtime.json` descriptor (`runtime-tree.ts`): schema version, release (shell, dsh, Host, Node, pnpm versions), platform, arch, shared package records, and a per-file `{path, bytes, sha256, executable}` inventory. `writeDesktopRuntimeAsync` seals it after materialization **and after native signing**; `verifyDesktopRuntime` (called from the electron-builder `afterPack` hook, `scripts/electron-builder-config.mjs`) recomputes the inventory with bounded concurrency (8 workers, drain-then-fail so no descriptor leaks) and fails the build on any difference. Startup deliberately does **not** re-verify; it reads metadata and checks shared-package records only **(README: re-adding startup comparison requires a concrete failure)**. Paths from metadata go through `runtimePath`, which refuses empty, absolute, backslash, colon, `.`, `..` segments.
- **Core package set.** `core-package-set.ts` defines a closed schema (`name` pattern, `version` pattern, `.tgz` file pattern, `sha512-` integrity) for tarballs of the release closure. First launch never installs core packages; the profile installs only external plugins.
- **Recovery that disables third-party plugins.** `fatal-recovery.ts` offers Exit, Restart, "Disable third-party plugins, back up profile patch, and restart", and "Get diagnostic report". The disable action calls the shared recovery function under the profile transaction lock and renames the profile `cordis.patch.yml` to a timestamped `.bak` **without parsing it**; the next start writes an empty patch; installed packages and earlier backups stay **(docs/diagnostics/README.md)**. `main.ts` wires `disablePlugins` to `DesktopProjectManager.disableAllPlugins()`. A known mandatory-update block refuses plugin mutations without stopping the Host **(README)**.
- **Pnpm and dependency runtimes are bundled** (primary-runtime: Node, pnpm, Python with a locked Office library set), installed offline on first use, version-bound to the Desktop release **(README, Key technical decisions)**.

**Additional findings (verified, pass 2).**
- **Profile lock is a pid file, not an advisory lock** (`project-manager.ts withLock`): `lock` is created with `wx` (mode 0600) holding the owner pid and an `fsync`; an existing lock must be a regular file (a symlink or non-file is an error), a live pid (`kill(pid, 0)`, any error other than `ESRCH` counts as alive) blocks the operation, and a dead pid's lock is removed and retaken. The operation runs inside, the descriptor is closed and the file unlinked in `finally`. It is brittle against pid reuse; the single-instance lock above is the real guard.
- **Dependency lifecycle scripts are an explicit allowlist.** The generated runtime-project `pnpm-workspace.yaml` (when core package overrides exist) sets `nodeLinker: hoisted`, `autoInstallPeers: false` and an `allowBuilds` map that enables build scripts for `node-pty`, `koffi`, `fs-ext` and the core build package and **disables** `@google/genai`, `protobufjs` and `node-addon-require-builtin`. A legacy settings file is migrated only when its text equals a known legacy string after CRLF normalization, so a user-edited file is never rewritten.
- **Recovery is a locked rename.** `disableAllPlugins()` takes the same lock and calls the shared sanitizer; `applyRelease()` validates the runtime descriptor first, then migrates settings, creates the plugin profile and removes link projections, all under the lock, without installing anything.
- **Release metadata is strict.** `parseDesktopRelease` rejects any `schemaVersion` other than 1 and any `hostProtocolVersion` other than the compiled constant, so a Host and shell from different releases cannot start together.
- **CLI command ownership** (`command-installation.ts`, `command-management.ts`, `command-manager-entry.ts`): a worker child (the bundled Node, a fixed entry) is the only code that touches `/usr/local/bin/dsh` or the user PATH. Every mutation carries a 64-hex fingerprint of the observed entry plus receipt (device, inode, mode, uid, gid, size, mtime for the entry; the receipt is at most 8 KiB with a strict schema); a changed entry returns `ESTALE`, a foreign or missing backup returns `EOWNERSHIP`. ## 5. Settings and local state

Three independent, shell-owned stores, all outside the product's own configuration:

1. `userData/desktop/settings.json` (`settings-file.ts`, `settings.ts`, `update-settings.ts`). Read once at startup. `DesktopSettingsFile.read()` never creates the file; the explicit startup `initialize()` creates it exclusively (`wx`, mode 0600, directory 0700) with `allowTestAuthPopupWindow: false` and never replaces an existing or invalid file **(verified, pass 2)**; fields validate **independently** with Zod (an invalid popup flag does not invalidate a valid channel); unknown fields survive a read-modify-write; saves share a writer lock with startup initialization; write diagnostics distinguish "no write", "uncertain completion" and "committed, then lock cleanup failed". Channel changes go through IPC with a pending/applied/failed result, and an **uncertain** save suspends update operations until the user reloads (an explicit "Reload settings" action that never rewrites the file). **(README, Local desktop settings; `main.ts` updatesChannelSet handler.)**
2. `userData/keybindings.json` (`keybindings.ts`, `keyboard.ts`): device-local, separate from `DSH_HOME`, versioned, serialized single-writer, failed reads retain last accepted bindings and block edits, future-version files stay unchanged.
3. `userData/desktop/locale-cache` (`locale-cache.ts`): last confirmed UI language, so the native recovery dialog can speak the right language when the Host cannot start. Write failure never blocks.

Plus small markers: `background-close-confirmed` (acknowledgement under userData), `plugin-operations/operations*.jsonl` (Section 8), and `update-cleanup.jsonl`.

`README.md` states the ownership rule: shell-local settings are those that must be readable when the Host is not running; everything else belongs to Host configuration.

**Additional findings (verified, pass 2).**
- **Fail closed on unreadable settings.** `readDesktopSettings` returns `allowTestAuthPopupWindow: false`, with a warning (path and error, never contents) when the file is unreadable, malformed or holds an invalid value; an absent field is `false` without a warning. A changed popup preference needs a restart; `DesktopUpdateSettings.load()` returns an error result for an explicitly invalid `channel`, which suspends updates, while absence uses the channel sealed into the packaged manifest (`dshDesktopUpdateChannel`; older manifests mean nightly).
- **Write outcomes are classified, not guessed.** `saveUpdates` takes the shared file lock, reads, merges only known keys over the existing document (unknown root and `updates` keys survive), and writes with `writeFileAtomic`. A failure carries `effect: unchanged | unknown | written`. `channelSaveFailure` maps `unknown` to the user-visible reason `uncertain`. Any write-kind failure (including `written` with a failed lock release) appends a record to `settings.json.save.jsonl` (mode 0600) with time, effect, path and reason; the error is rethrown unless the effect was `written`.
- **Versions are never guessed.** `desktopClientVersion()` throws if the build carries no `DSH_CLIENT_VERSION`; `DesktopMandatoryUpdatePolicy` rejects a non-semver client or bundled version at construction.
- **Tray and acknowledgement markers.** `DesktopBackgroundNotice` treats only an explicit button click as acknowledgement (a dismissed prompt stays eligible), coalesces repeated close requests, and a marker write failure only warns; the Windows tray exists for the whole run and its quit entry uses the same confirmation as every other quit.
- **Cached locale is validated.** `readDesktopLocaleCache` accepts a value only if `resolveDesktopLocale(value).id === value`, so a non-canonical string is rejected rather than coerced.

## 6. State management inside the shell

The shell uses explicit small state machines with generation counters instead of ad hoc flags.

- **`DesktopBackendController`** (`backend-controller.ts`): phases `starting | ready | error`; each start creates an `Attempt {cancelled, failure, host, cleanup}`; concurrent `start()` calls share one pending promise; `stop()` marks the attempt cancelled, awaits both its own cleanup and the pending start, and refuses new starts while stopping; `close()` is permanent; a failure after `ready` flips to `error` and still schedules cleanup; cleanup errors are aggregated with the original failure (`AggregateError`). Listener exceptions are caught and logged so a UI bug cannot break lifecycle.
- **`DesktopUpdateCoordinator`** (`update-coordinator.ts`): state `idle | checking | available | downloading | verifying | installing | ready | error` plus a `release` union `none | checked | downloaded | handed-off`. A **generation** counter is incremented on channel switch; every async continuation compares its captured generation and returns the current state if stale. `check/download/install/switchChannel` are single-flight (`??=` on an operation promise). `autoDownload = false` and `autoInstallOnAppQuit = false`: nothing downloads or installs without a user action. Install is `quitAndInstall(true, true)` only after `beforeRestart()` returns true; any exception or `error` event while installing becomes an `install` failure.
- **`DesktopUpdateSchedule`** (`update-schedule.ts`): base interval 10 min, exponential doubling on failure to a 1 h cap, uniform jitter within plus or minus 20%, floor 1 s, manual checks bypass the deadline and join an in-flight check, advance of the delay happens once per joined batch, monotonic clock (`performance.now`).
- **Presentation split**: `DesktopUpdateState` (full, main-owned, includes diagnostics) vs `DesktopUpdatePresentation` (semantic projection sent to renderers: phase, version, percent, failure kind, configuration error). The renderer never sees raw error text, URLs or authorization; failure copy is chosen by a typed `preparationFailure` kind so translations cannot reclassify a failure.

**Additional findings (verified, pass 2).**
- **UI flows carry a revision.** `openUpdatePrompt` in `main.ts` captures `updates.revision` before awaiting and abandons the flow if it changed; the same revision is passed to `install(version, revision)`, so a stale confirmation after a channel switch is a no-op (`update-coordinator.spec.ts`: "retires a downloaded target and rejects its old confirmation after switching").
- **Single-flight at every UI layer.** `promptOperation`, `authenticationOperation`, the dialog (`DesktopUpdateDialog` replaces the active prompt and cancels the old one), the quit prompt and the command manager each join callers to one in-flight promise.
- **Dialog responses are revision-stamped.** `DesktopUpdateDialog` increments `revision` for every view; `respond(revision, index)` throws on a stale revision or an index outside the displayed buttons, ignores clicks while a button is `busy`, and holds a busy state at least 500 ms so a fast local action is still perceptible. Closing or replacing a dialog resolves to its cancel id and never grants anything.
- **Mandatory confirmation is a small state machine** (`mandatory-update-window.ts`): `confirmation = {version, active, revision}`; `install` or `later` must repeat both the version and the revision; `later` is accepted only if the confirmation says tasks are active; `refresh`, `download` and `install` share one `action ??=` promise; a failed shell view load triggers a native fallback dialog offering "download page" (allowlisted URL only) or "quit"; a crashed shell view reloads.

## 7. Rendering and streaming UI

The shell itself renders very little: update dialogs, the mandatory overlay, welcome/onboarding, and the Windows caption menus. The product UI streams from the Host over the proxied HTTP/WebSocket endpoints. What is instructive:

- **Cold start ordering** **(README, Runtime and plugin activation)**: the main window loads the shared loading page offscreen from packaged assets *before* profile preparation and Host start; the login-shell environment read runs in parallel with profile preparation (`main.ts reconcileBackend` awaits `manager.applyRelease()` and `prepareHostEnvironment()` together); the page waits on the boot promise and then starts the client without navigating to another document, so there is one document for the whole session.
- **Hide, do not close.** Closing the main window hides it; the page, Host and tasks keep running and the same document (with drafts and scroll position) returns on show (Dock, second launch, `dsh://open`, tray). macOS leaves fullscreen first. A first-close acknowledgement on Windows is stored as a marker file.
- **Native overlays inside the window.** Update dialogs are `WebContentsView`s inside the owner (not separate OS windows), with input blocking tracked by revision so keyboard shortcuts and editing keys cannot reach the parent or browser guests while an overlay exists (`update-overlay.ts`, `keyboard.ts`). On Windows the mandatory overlay is an in-DOM shell frame whose actions travel over a private `MessageChannel`; the README is explicit that the shared DOM is **not** a security boundary and that product scripts can hide it but cannot clear main-process policy.
- **Native window material**: Windows 40-DIP caption with synchronized colors; macOS vibrancy with an opaque base while minimized or hidden to cover a known reattach gap (`main.ts` applyBackdrop). Reduce Motion, Reduce Transparency, Increase Contrast honored on the welcome window.
- **Streaming**: HTTP bodies and aborts are piped through unchanged; WebSockets connect directly to the Host with credentials injected by header rewriting rather than JavaScript.
- **Bounded native drag/drop**: file drag stages arbitrary bytes or Host-authorized resource references; total temporary + retained exports capped at 64 MiB, unused files released on pointer leave, OS-delivered copies expire after 60 s, system icons loaded asynchronously so large images are never decoded in main (**README**; `file-drag-files.ts`).

**Additional findings (verified, pass 2).**
- **Keyboard interception is an input state machine** (`keyboard.ts`): shortcut matching is by physical `code` plus modifiers and optional two-key chords built from currently held keys; IME composition, `Dead` keys and AltGr are never matched; held-key and consumed-key sets reset on window blur, main-frame navigation and any change of the overlay-input revision; the keyup of a consumed press is also prevented so renderer handlers see a balanced pair; during recording, Electron's menu shortcuts are suppressed with `setIgnoreMenuShortcuts`; guest webviews (leased) get the same handler, bound to a lease name; editing keys sent from the Windows caption menu are replayed as synthetic key events so editor-owned undo stacks see them.
- **Update and mandatory overlays are `WebContentsView`s** inside the owner (`update-overlay.ts`): resize tracks content bounds minus the 40-DIP Windows caption, the owner's `before-input-event` is blocked while any overlay exists (a counter plus a revision), focus returns to the owner when the overlay is released, and `window.open` is denied.
- **Welcome page** (`client/WelcomePage.tsx`, `welcome-window.ts`): fixed 600 by 700, sandboxed, no navigation and no popups; the API key field is a password input with `autoComplete="new-password"`; client and main both require printable ASCII (`^[\x21-\x7e]+$`), and the client also rejects `NAME=value` pastes and values wrapped in quotes or backticks; save returns only `{ok}` and never provider diagnostics; analytics calls pass a closed shape check per event name and are sent only while the live collection policy reads enabled.

## 8. Crash recovery and diagnostics (high-value for 018 and 011)

This is the most directly reusable subsystem in the app.

- **One fatal dialog per process.** `DesktopFatalRecovery.report` sets `reported` once; the dialog shows a bounded tail (8 lines, 1,200 UTF-16 units, with a truncation notice and surrogate-pair repair) of the first error plus the crash-report status ("pending", "unavailable" or the path). `EADDRINUSE` is recognised and removes the plugin-disable option (disabling plugins cannot fix a port clash). The dialog loops: "Get diagnostic report" reveals the file and returns to the dialog; Exit/Restart/Disable stop the Host first and, if a recovery step fails, re-show the dialog with a recovery-failure headline instead of quitting.
- **Crash report file** (`crash-report.ts`): `crash-<UTC>-<source>.log`, source in `host | web-boot | renderer | main`, `phase` (`startup | running`), application and runtime versions, the error with enumerable properties and cause chain (capped at 256 KiB), the Host's own diagnostic (64 Ki tail of stderr plus startup metadata), a tail of renderer error-level console lines, owner-only permissions, the ten newest kept, older pruned by exact filename pattern only. The shell waits at most 1 s (`CRASH_REPORT_WAIT_MS`) for the report before opening the dialog; a slow disk shows "pending".
- **Operation journal** (`operation-journal.ts`): two JSONL segments (`operations.jsonl`, `operations.previous.jsonl`) of 256 KiB; records at most 4 KiB, no CR/LF; a queue capped at 64 KiB; **a partial trailing line is truncated at open**, an oversized segment is reset; any write failure disables the writer for the rest of the lifetime (no appending behind an uncertain partial write); `drain(timeoutMs)` is bounded (500 ms at exit, recovery and update) and a timeout aborts further writes. Records are validated and run-id matched in `host-process.ts` before enqueue.
- **Isolated, bounded report collection** (`operation-report-worker.ts`, `operation-report-job.ts`, `operation-history.ts`): after the basic report is saved, a `Worker` reads at most 64 KiB and 100 records from the two owned files, with a 500 ms budget (last 100 ms for cooperative cancellation before forced termination), one collector at a time, an explicit completion marker and omission counters. "A start without an end" is stated to not prove success.
- **Run identity**: the Host announces a `runId` (uuid) before profile loading; Host errors carry it as `hostRunId`; operation records are matched by it, so a report can distinguish "this run's records" from stale ones.
- **Update-install failure restores the Host** and keeps the downloaded target for retry (`main.ts publishUpdate`).
- **Update journal** (`update-journal.ts`): opt-in qualification evidence (`DSH_DESKTOP_UPDATE_JOURNAL_DIR`) that whitelists phase, version, integer progress, operation and a fixed error classification; no URLs, raw text, or unexpected fields survive.

**Additional findings (verified, pass 2).**
- **Crash report format** (`crash-report.ts`): file name `crash-<ISO time with : and . replaced by ->-<source>.log`; the file is created with `wx` (never overwritten), mode 0600 in a 0700 directory; the error section is `util.inspect` with depth 6, 64 KiB string cap, 100 array items and a 256 KiB total cap with an explicit truncation line; the renderer console tail keeps whole lines and one oversized line intact; pruning matches an exact filename regex and deletes the oldest beyond ten, logging (not throwing) on failure. Failure to write returns `undefined` and the dialog proceeds.
- **History reader** (`operation-history.ts`): reads the tail of the newest segment first, dedupes the two files by `dev:ino` (so a symlink or hardlink cannot double count), reads in 16 KiB steps while checking the abort signal, never parses an unterminated last line, counts oversized or invalid lines as `invalidRecords` instead of failing, and reports `truncated`, `unavailableFiles` and `cancelled` as facts. The report appends a header (journal status, counters, omissions), the records that fit the byte budget and a completion footer; a missing footer means the section is incomplete.
- **Worker lifetime** (`operation-report-job.ts`): validated deadlines (`timeoutMs > cancellationGraceMs >= 1`), a `Worker` with 32 MiB old-generation and 8 MiB young-generation limits, `postMessage('cancel')` at the collection deadline, forced `terminate()` after the grace, and the result is reported only after the worker's `exit` event.
- **Installed-update evidence is derived from the journal, not from the operator's memory** (`installed-update-qualification.ts`): per-process files `<epoch>-<uuid>.jsonl`, strictly increasing `sequence` from 0, a closed field set, fixed enums for phase, operation and error code, a 10 MiB per-file and 50 MiB total limit, an incomplete trailing line is an error. The inspector walks ten milestones (original workspace, first download, transfer started, download failed, manual retry, download ready, install confirmed, original quit, successor started, successor workspace) and always returns `operatorVerificationRequired` listing five items it cannot establish (feed publication after the original started, network fault and recovery, installer completion and installed path, test data preserved, screenshots and confirmations).
- **Packaging evidence** (`packaging-run.mjs`): every run has `run.json`, `events.jsonl` (flushed before the operation), redacted `stdout.log`/`stderr.log`, `result.json` and, on a fatal signing event, `fatal.json`. ## 9. Permissions and security (sandboxing, CSP, context isolation)

Window options (`main.ts createWindow`): `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, `webSecurity: true`, `webviewTag` only for the primary window. `setWindowOpenHandler` denies and opens `http(s)` externally; `will-navigate` blocks anything that is not the app scheme or same-origin HTTP. Preloads are CJS bundles that may only `require` `electron`, `events`, `timers`, `url` (enforced by `scripts/desktop-bundle-imports.mjs`, a bundler plugin run from `tsdown.config.ts`, so an unresolvable bare import fails the build instead of failing at launch).

**Other controls found in code:**
- **Webview leases** (`browser-guests.ts`): a guest may attach only with a lease issued to its owner, a partition keyed by workspace identity, no Node integration and no guest preload; release closes the guest and awaits `destroyed`; leases from another window are rejected.

## 10. Auto-update

Mechanism: `electron-updater` with `autoDownload` and `autoInstallOnAppQuit` off, channels `stable` and `nightly` chosen independently of version suffixes, downgrade disabled, differential blockmaps, SHA-512 verified, Windows publisher check derived from the signing certificate's `CN`, `O`, `C` into the shipped `app-update.yml` (the downloaded feed does not choose the publisher). The shell adds:

- **User-driven only.** Automatic checks never open dialogs or download; a user picks "download", then a ready confirmation, then a second approval that stops tasks.
- **Quiescence gate** inside `beforeRestart` (`main.ts`): wait for command management and workspace recovery to settle; inspect tasks; fullscreen exit (with timeout kind); confirm; analytics intake with a 1 s deadline (not LiteCowork-relevant); lock admission; close Platform view and await its storage cleanup; dispose file-drag; stop the Host *requiring graceful exit*; drain the operation journal 500 ms; only then hand off. Failure after Host stop restores a Host, navigates the existing window to reload page-owned state, and keeps the artifact.
- **Graceful stop ladder** (`host-process.ts stop`): send `shutdown`; wait 10 s; `SIGTERM`; wait 5 s; `SIGKILL`; wait 5 s; if still alive, error. With `requireGraceful`, a forced kill or a missing `shutdown-complete` acknowledgement exits the child but **refuses installation** with a typed `DesktopHostUncleanExitError`.
- **HTTP idle deadline**: no response headers or no bytes for the configured idle time (60 s in the real-Electron qualification fixtures; the constructor accepts 1 s to 2,147,483,647 ms) fails with `ETIMEDOUT` and aborts the request; every data chunk refreshes the timer, so there is no total-duration limit for active downloads (`DesktopUpdateHttpExecutor`, `update-http-executor.spec.ts` not read) **(verified, pass 2)**.
- **Channel switching** is transactional: persist, bump generation, cancel token, await in-flight check and download, discard cache (`discard.ts`), set new channel, re-check; a cleanup failure suspends configuration; never auto-downgrade.
- **Cleanup log**: obsolete-file removal failures after eligibility is revoked go to `update-cleanup.jsonl` with time, operation, path and error, falling back to stderr.
- **Hidden-window rule**: a download that finishes while the window is hidden defers the install confirmation until shown; the mandatory flow uses taskbar attention or a Dock bounce plus one silent notification, never focus stealing (`update-attention.ts`).
- **Qualification layers** (tests/README.md): local loopback server with real Electron HTTP and `NsisUpdater`; channel tests; real-Electron mandatory renderer; Windows installed-update operator checklist with a journal; update-signature test using the real publisher verifier.

**Additional findings (verified, pass 2).**
- **Installation handoff is `quitAndInstall(true, true)` after `beforeRestart` resolves true**, and any exception, `error` event or false result keeps the prepared package and reports an `install` failure (`update-coordinator.ts`; the spec pins "retains an asynchronous installer failure after quitAndInstall returns" and "refuses handoff after failed task preparation while retaining the prepared package"). 100 percent download progress never equates to readiness; readiness waits for the updater's verified download and platform preparation.
- **Private library state is a known risk, and it is contained.** `discard.ts` reaches into `electron-updater` 6.x private fields (`updateInfoAndProvider`, `downloadedUpdateHelper`, `server`, `squirrelDownloadedUpdate`) to revoke a pending target, closes the macOS local feed server, clears the in-memory target and removes the pending-update cache directory file by file, writing failures to `update-cleanup.jsonl` instead of throwing. It refuses if a native installation is already staged. The file says it is covered by real-library tests. `update-channel.ts` re-applies `allowDowngrade = false` after the library's channel setter (which enables downgrades). Treat both as examples of why a pinned dependency needs a real-library test.
- **Failure taxonomy.** `update-presentation.ts` defines 14 failure kinds (`configuration`, `check`, `check-network`, `download`, `download-space`, `-permission`, `-busy`, `-network`, `install`, `install-network`, `stop-failed`, `tasks-changed`, `tasks-unavailable`, `fullscreen-timeout`). Network failures are recognized by a regex over five error codes; filesystem causes come from the `ENOSPC`, `EACCES`/`EPERM`/`EROFS` and `EBUSY` codes (`update-error.ts`). The renderer receives only the semantic projection; raw text, path and destination appear only in a separately expandable "technical details" field built by the main process.
- **Attention without authorization** (`update-attention.ts`): when the install confirmation is waiting and neither window is focused, Windows flashes the taskbar, macOS bounces the Dock once, and one silent notification is shown; clicking it returns to the confirmation and installs nothing; any focus clears it; one reminder per downloaded version.
- **Fullscreen preparation** (`update-window.ts`): leaving macOS fullscreen is awaited with a 5 s deadline, a closed window cancels the install, and an elapsed deadline raises a typed preparation failure (never authorization).
- **Windows publisher pinning** (`windows-sign.mjs resolveWindowsUpdatePublisher`): `CN`, `O`, `C` from the public certificate, each present and single-valued, with `\\`, `"`, `,`, `;`, `+`, spaces and control characters hex-escaped for the DN; macOS writes `app-update.yml` (generic provider, channel, cache directory name) before signing and re-verifies it in the final app (`macos-app-update-config.mjs`).
- **Quit sequence** (`main.ts finishQuit`, `before-quit`): when the installer owns the quit (`shellInstallerOwnsQuit`) the shell disposes dialogs and the tray and lets Electron quit; otherwise it hides windows, then cleans up in parallel with each error caught and logged (operation reports, policy client then policy login, `backend.close()` then a 500 ms journal drain, Platform view, file drag) before `app.quit()`.

## 11. Packaging, installer, signing, publishing

(Pass 1 rested on README prose and leading doc comments. Pass 2 read the signing, notarization, packaging-supervision, publishing, rollback, installed-update, runner-setup and installer sources line by line; Section 0 lists the roughly 6,400 script lines still unread. Subsections 11.1 to 11.7 below are the verified detail; the paragraphs before them are the pass 1 summary, kept because the code confirmed them.)

**Build structure.** `tsc -b` then `tsdown` bundles `main.js`, preloads (CJS), a worker and a command-manager entry; the Welcome page is built by Vite as an IIFE inside the tsdown `onSuccess`. The workspace tsdown pass must finish first because the main bundle inlines workspace devDependencies from their output; `desktop-bundle-imports` fails the build if a bare import could not resolve in the packaged app. `electron-builder` config is generated by `createElectronBuilderConfig(env, ...)` from one release environment, with hooks `beforeBuild` (compile the NSIS native helper, render installer strings), `beforePack` (compute Office and native asarUnpack patterns, validate policy), `afterPack` (write macOS updater config, **verify the sealed runtime inventory**, verify unpacked PE files) and `afterSign` (sign Windows PE files in the output, verify). Native binaries (`.node`, `.dll`, `.so`, `.exe`, `spawn-helper`, ripgrep) are `asarUnpack`ed.

**Release identity.** One version string covers shell, dsh runtime, Host and pnpm. Production uses the dsh base version exactly; test builds append `.YYYYMMDD.index` (or `-test.` for a stable base) in the Asia/Shanghai date; `--build-version auto` proposes the next free index by reading published objects, falling back to local artifacts; a build commit and dirty flag are recorded in manifest metadata; production uploads tag `desktop-v<version>` *after* artifacts are public and a tagging failure never fails a finished upload. Unsigned artifacts carry a filename suffix so they cannot pass for release artifacts. **(packaging/README.md)**

**Windows signing.** EV code-signing certificate on a hardware token, via a SafeNet-compatible SignTool, with: a supervised preflight that signs and verifies a throwaway probe before building; an on-disk **attempt interlock** (`%USERPROFILE%/.dsh-desktop-signing/attempt.json`) acquired before the token is touched and released only after a successful sign plus verification of the primary signature; `SignTool Error: No private key is available.` treated as fatal (stop all retries to avoid locking the token); timestamping completed afterward on isolated copies without credentials, three attempts with 1 s and 2 s delays, retried only on a normally-exited failure; a **content-addressed signature cache** shared across worktrees (policy-bound key, account-owned directory, no linked paths); PE discovery that reads headers of every regular file (including extensionless), rejects links and malformed `MZ` files, and runs trust checks in batches of 32 with at most four processes; a final PE-signature audit and a fresh-cache ASAR/Host smoke before the completion record is written. Signing credentials are withheld from build subprocesses.

**macOS.** Hardened runtime with entitlements (JIT for Node/V8 and, on x64, unsigned executable memory), per-file signature cache bound to certificate, tools, identifier and entitlements, a temporary signing keychain per invocation, notarization via separately timed `notarytool` phases, DMG notarized and stapled separately from the ZIP, a notarization-proxy transaction with recovery records. (V1 LiteCowork has no macOS row.)

**Windows installer.** Custom NSIS with a native GDI+ progress page: a single opaque pixel buffer, static art drawn once; directory **transaction** (stage then rename a complete directory), new destinations must be empty and non-empty destinations must be registered installations; drive roots rejected after normalization; per-user only; silent update waits up to 10 s for the old app to exit then stops with exit code 2; the uninstaller removes Electron user-data and cache but **never the product data home**, protects overlap with `DSH_HOME`, refuses protected Windows folders, requires a fixed local drive, unlinks reparse points without entering them; an update-triggered uninstall (`--updated`, `/KEEP_APP_DATA`) retains data. Per-language NSIS strings are generated from the eight locale JSON files and the native installer test builds each language.

**Packaging supervision and evidence.** Every package command writes `.desktop-build/packaging-runs/<id>/{run.json, events.jsonl (flushed before each operation), redacted stdout/stderr logs, result.json, fatal.json}`; a fatal signing failure makes the supervisor terminate the stage process tree; failed stages cannot start later ones. Toolchain preflight probes archive tools and the NSIS compiler *before* the first long stage (`desktop-toolchain-preflight.ts`). A completion record exists only after signing, notarization and runtime verification.

**Publishing.** Packaging does not upload and strips COS credentials from child processes. Upload validates the completion record, deployment, target, version, filenames, sizes and SHA-512 *before reading credentials*; **binaries and blockmaps first, then channel YAML**; historical objects retained; unknown write outcomes reconciled by reading remote bytes; conflicting same-name bytes stop the operation; a newer channel version blocks a stale upload; durable `plan.json` / `events.jsonl` / `result.json` per attempt, with PUT intent flushed before the request, no credentials or raw SDK errors recorded, audit failure stops later writes. Fixed-name "latest" installers are a separate upload with `Content-Disposition` and a CDN purge whose acceptance (not completion) is reported and never auto-retried. CI publication runs on the **original build machine** from retained artifacts (so the signed bytes never travel through a hosted runner), requires GitHub Environment approval, has per-channel machine locks, tags with a short-lived GitHub App token, and offers a read-only-preview channel rollback script that restores historical feeds without moving binaries or tags (`scripts/rollback-desktop-channel.ts`, `desktop-rollback.ts`). **(publishing/README.md, publishing/ci/README.md)**

### 11.1 Windows signing (verified, pass 2)

- **Hook contract** (`windows-sign.mjs createWindowsTokenSigner`): the electron-builder hook is serialized through one promise chain; it rejects any hash other than SHA-256 and any appended signature; it first offers the file to `preserveSignature` (vendor-signed copies that are byte-identical to the prepared source and already `Valid` are kept without touching the token); it needs a supervised run directory; it validates the certificate file is a non-CA code-signing certificate and the SignTool is a real `.exe`; the PIN may not contain `]`, quotes or line breaks (SafeNet key-container syntax) and is the only secret redacted from diagnostics.
- **Sign once, then finish without hardware** (`windows-timestamp.mjs completeWindowsSignature`): copy the input to a short private staging path (under 260 characters), sign the copy once with `windows-sign.cmd` under the attempt interlock, verify the primary signature (`Valid`, not yet timestamped, thumbprint equal), freeze its digest, normalize a copy (`signtool remove /u`; exit code 2 is tolerated only if the bytes are unchanged), then up to three timestamp attempts each on a fresh copy of the frozen signed bytes (retry only on a normally exited failure with code 1 or 2, waiting 1 s then 2 s); every attempt re-verifies `Valid`, timestamped, thumbprint equal; normalizing the timestamped copy must equal the baseline so a substituted payload with a valid signature is rejected; the target is replaced by copying to a `.complete-signature-*` directory on the same volume and a `rename`, then re-hashing; on any failure the staging tree is copied to `signature-failure-*` evidence (or kept in place if evidence cannot be stored) and the original input is left untouched.
- **CMD shim** (`windows-sign.cmd`): disables delayed expansion, copies the six `DSH_DESKTOP_WINDOWS_*` values into local variables, **clears the environment variables before SignTool starts**, and calls SignTool with `/fd sha256`, `/f cert`, `/kc "[{{PIN}}]=container"`, `/csp "eToken Base Cryptographic Provider"` and no timestamp. The Node side invokes it with `cmd.exe /d /v:off /c`, a scrubbed environment and a failure that is rewritten without the original error as `cause` (the raw error would contain the PIN-bearing command line).
- **Interlock and fatal marker** (`windows-signing-state.mjs`): `attempt.json` is created with `wx` under `%USERPROFILE%/.dsh-desktop-signing` before the child starts and holds attempt id, run directory, pid, time and target; success deletes it only after reading it back and matching the id; failure records the event and calls `failPackagingRun`, which writes `fatal.json` and prints `DSH_DESKTOP_PACKAGING_FATAL` so the supervisor kills the stage's process tree. A spec (`windows-signing-state.spec.ts`) races two independent processes and requires exactly one to acquire, and a third attempt after both exits to be blocked.
- **Preflight** (`windows-signing-preflight.ts`): refuses if `fatal.json` or `attempt.json` exist, checks the certificate validity window, hashes the compiler, SignTool and certificate into the journal, compares the token's public keys with the certificate **without a PIN** (`windows-token-identity.ts` parses both RSA slots from a PowerShell 7 helper under a 15 s timeout, compares SPKI bytes, and returns one of five results), compiles a never-executed probe with the .NET Framework compiler, requires it to be unsigned, signs it through the production signer, and requires `Valid`, timestamped and the right thumbprint. The `.cs` helper that reads the key containers was not read.
- **Runtime code** (`windows-runtime-signature.mjs signWindowsCode`): enumerates regular files only, rejects any symlink, reads the 64-byte header of each file with at most eight open files (an `MZ` file without a valid PE signature, or any `.exe`/`.dll`/`.pyd` that is not a PE, fails the run), inspects signatures in PowerShell batches of 32 files with at most four processes at once and requires every output row to match its requested path, refuses any status other than `NotSigned` or `Valid`, restores from the cache with bounded workers and verifies, signs the remainder one at a time and verifies each. `signWindowsDesktopRuntime` signs, then **rewrites the sealed descriptor**, verifies it again, smokes, and verifies a third time.
- **Signature cache** (`windows-signature-cache.mjs`): key = SHA-256 of `{version, inputDigest, identity}` where `identity` hashes the certificate, SignTool, `windows-sign.cmd`, `windows-sign.mjs` and `windows-timestamp.mjs`; an entry is a `record.json` plus a `payload`; every use re-checks the payload digest, then Windows trust, timestamp and thumbprint, then replaces the target by `rename` after checking it is unchanged; a new entry is staged in `.publish-*` and renamed (`EEXIST` means another process won, and the winner is revalidated); migration and maintenance (`--usage`, `--clear`) reuse the same entry reader and never touch incomplete staging names.
- **Stage lock** (`windows-signing-stage.mjs`): an exclusive `CreateFileW` (share mode 0) on `stage.lock` through `koffi`, polled every 100 ms on `ERROR_SHARING_VIOLATION`, abortable, with wait time recorded; closing the handle releases it even if the process dies. It guards preflight, primary-runtime, dsh-runtime and artifact stages; it is separate from the hardware interlock.
- **Fragile hook (call out).** `installWindowsNsisBootstrapSigner` patches `WineVmManager.prototype.exec` from `app-builder-lib` so that the temporary NSIS bootstrap executable (recognized by `__COMPAT_LAYER === 'RunAsInvoker'`) is signed before it runs under enterprise code-integrity policy. It relies on a private builder detail; the signing hook itself also repairs a "dangling Authenticode directory" (a certificate-table entry pointing past end of file) by zeroing the entry before signing.
- **Measured throughput** (`tests/signing-concurrency/README.md`, one host, one token): 156 files, 849 MiB; serial 725 s; two completion workers with two hardware requests 397 s (fastest); four with four 462 s; four workers with one hardware request 428 s. The README concludes that pipeline overlap supplies most of the gain and keeps production signing serial.

### 11.2 macOS signing and notarization (verified, pass 2)

- **Temporary keychain** (`macos-signing-keychain.mjs`): a keychain in a temp directory with a random 32-byte password, the p12 imported with `-T codesign -T productbuild`, a key partition list for Apple tools, prepended to the user keychain search list (because `codesign` ignores `--keychain` otherwise) and restored before deletion; a probe copy of `/usr/bin/true` is signed with the Developer ID and verified before any work starts; the child environment loses `CSC_LINK` and `CSC_KEY_PASSWORD` and gains `CSC_KEYCHAIN`. Command failures are rewritten without arguments because `execFile` errors embed the command line.
- **Runtime Mach-O signing** (`macos-runtime.ts`): inventory from the sealed descriptor, Mach-O recognized by magic bytes; each file gets identifier `<appId>.runtime.<sha256(path)>`, hardened runtime and secure timestamp; Node and the LibreOffice kit get JIT entitlements (x64 Node gets a different plist); already-notarized Computer Use helper bundles are verified (deep signature, identity, stapled ticket, Gatekeeper) and **not** re-signed; four workers; `AggregateError` on failure; thin binaries use a mode-preserving content-addressed cache whose key includes input digest, permissions and the full signing policy, pruned to one GiB.
- **Notarization** (`logged-notarytool.mjs`): `submit --wait` is split into `submit --no-wait`, a UUID check on the returned id, and `wait <id>` with timings per phase; the wait result id must equal the submission id; a non-`Accepted` status returns the output so the library can fetch the log; diagnostics are redacted and recorded. After acceptance the app is stapled by `@electron/notarize`, and `verify-macos-signature.mjs` runs `codesign --verify --deep --strict`, checks `Authority=Developer ID Application: <identity>` and `TeamIdentifier`, and for runtime files requires a `Timestamp=` line and `flags=...(runtime)`; DMGs get `stapler validate` and `spctl --assess --type install`.
- **Two artifact lanes** (`package-macos.ts`): the signed app is copied twice with `ditto`; the ZIP lane notarizes and staples its copy and then builds the ZIP and update metadata, the DMG lane builds a DMG around its copy and notarizes the DMG; both lanes settle (`allSettled`) before anything is promoted; artifacts must exist and be non-empty; only then are files renamed into the artifacts directory and the stapled app replaces the directory build.
- **System proxy transaction** (`macos-notarization-proxy.ts`): a per-user flock, a recovery record written before any change, refusal if PAC, proxy auto-discovery, SOCKS or an authenticated proxy is configured, restoration after SIGINT/SIGTERM only once work has settled, and a `restore:mac-proxy` recovery command. LiteCowork has no macOS row in V1, so only the principle (never mutate shared system state without a lock, a recovery record and a restore command) is reusable.

### 11.3 Packaging supervision and environment hygiene (verified, pass 2)

- **Configuration is read from allowlisted keys.** `loadDesktopPackageEnvironment` builds the child environment from the parent minus every ambient release-shaped variable (`DSH_DESKTOP_APP_ID`, `DSH_DESKTOP_AUTO_UPDATE_ENV`, `DSH_DESKTOP_MANDATORY_UPDATE_*`, `DSH_DESKTOP_WINDOWS_*`, `DSH_DESKTOP_MACOS_*`, `APPLE_*`, `CSC_*`, `WIN_CSC_*`, `DOWNLOAD_TEST_*`, `DOWNLOAD_PROD_*`), then adds only the keys a regex allows from the selected dotenv or machine preset, and secrets only from a separate `secrets/` file and only when signing; a preset's `DSH_DESKTOP_AUTO_UPDATE_ENV` must equal its name. `validateDesktopPackageEnvironment` runs before any build and exercises the signer constructor, the cache directory resolver, notarization strategy exclusivity (exactly one of Apple ID, API key, keychain profile) and readable credential files.
- **Subprocess environments are narrowed per stage** (`package-target.ts`): build steps lose Windows signing fields and COS upload credentials; only the electron-builder and primary-runtime signing stages receive the signing fields; unsigned builds drop `CSC_*`, `APPLE_*`, macOS signing keys and force `CSC_IDENTITY_AUTO_DISCOVERY=false`; `ELECTRON_BUILDER_7Z_FILTER=BCJ` is forced for Windows because the bundled NSIS decoder cannot extract the automatic ARM64 filter. The completion record `<target>-release.json` is deleted at the start of a release build and written (via a temp file and rename) only after every stage and smoke test passes.
- **Run supervisor** (`packaging-run.mjs`): stages run sequentially unless parallel mode is on; a fatal marker on stderr or an existing `fatal.json` makes the supervisor kill the whole process tree (`taskkill /T /F` or a negative-pid `SIGKILL`) and wait; timeouts, launch errors, output errors and termination errors are separate recorded facts; `SIGINT` and `SIGTERM` stop the stage before the process exits.
- **Template patching fails loudly.** `windows-directory-installer.mjs` edits the pinned electron-builder NSIS templates through `replaceOnce`, which throws if the expected text is not found exactly once, so a builder upgrade that changes a template breaks the build instead of silently producing a different installer.
- **Patch and runtime dependency policy.** `runtime-patch-policy.ts` classifies every workspace patch as `shared`, `workspace-only` or `runtime-only` with a written reason; unclassified or stale entries stop packaging (README). Reviewed dependency overrides are listed separately.

### 11.4 Publication, retention and rollback (verified, pass 2)

- **Plan before credentials** (`desktop-upload-plan.ts`): the completion record's schema, target, channel, environment and public URL must equal the selected destination; the build version must be valid for the product version; the update metadata must name exactly one file whose URL basename equals the expected installer name, with size and SHA-512 verified against the disk; blockmaps must exist; the published YAML is rewritten with absolute payload URLs and an optional `stagingPercentage`; the fixed "latest" installer is a separate plan with a `Content-Disposition` attachment name.
- **Publish reconcile** (`desktop-publish.ts`): every feed is pre-read; a remote feed with a newer version is `superseded`, the same version with different bytes is `conflict`; then every binary and feed is hashed locally and read from the remote (streamed hash; channel files capped at 1 MiB); equal bytes are skipped, a differing binary is a `conflict`, a feed that changed since the pre-read is `remote-changed`; `put-intent` (with before and after YAML for feeds) is flushed, the PUT carries `x-cos-forbid-overwrite` for binaries only, and a read-back must match before `put-verified`. Production requires a clean 40-hex packaged commit. The tag is created last; a tag failure returns `published-tag-pending` and, on retry, `wasDesktopAttemptPublished` finds a newline-terminated `feeds-complete` event and allows tag recovery only (a different staging percentage is an error).
- **COS client is configured so the SDK cannot repeat a write** (`desktop-cos.ts`): `ChunkRetryTimes: 0`, no redirects, no host switching, no clock-skew correction, `KeepAlive: false`, a 15-minute request timeout, and the SDK's empty `Cache-Control` header removed; bodies are streams with explicit length and `Content-MD5`. `cos-operation.ts` wraps one operation in a total deadline, aborts the HTTP request through an `AbortSignal` injected into the SDK's HTTP modules and awaits socket close before returning.
- **Retention and approval** (`desktop-release-store.ts`, `publish-desktop-ci.ts`, `resolve-*`): the original machine copies an explicit file list (filename allowlist `^[a-zA-Z0-9][a-zA-Z0-9._-]*$`, no directories, no `manifest.json`), hashes before and after the copy, writes a strict manifest with SHA-512 per file, and publishes the attempt directory with a `rename` guarded by a claim directory. At publish time the manifest is re-verified, the GitHub run attempt, job conclusion and runner name must match, the source commit must be reachable from the selected branch or equal the tag, the deployment Environment must have required reviewers, signatures are re-checked on the original platform (Windows Authenticode thumbprint and timestamp; macOS DMG plus a ZIP extracted after a path-traversal check, then `stapler` and `spctl`), and a SHA-256 over the manifest and plan is shown for approval and **recomputed after approval; a mismatch stops publication**. Production origin and the GitHub App configuration are fixed in code.
- **Rollback** (`desktop-rollback.ts`, `rollback-desktop-channel.ts`): previews by default; verifies every historical binary is byte-identical on the remote; only a feed whose current version equals `--expected-version` may be replaced; re-reads before each write; never calls the tag operation; records intent, verification and completion in a new journal.
- **Purge recovery** (`desktop-purge-recovery.ts`): the record is saved as `pending` before the request; a lost response triggers a history query inside a 120 s window to correlate the task; ambiguity is `unknown`, not success; observation is bounded with one extra query; a confirmed failure throws; resubmission needs an explicit flag. Job ids that contain the secret id or key are rejected.
- **Credential launcher** (`upload-with-credentials.ps1`): Windows DPAPI `SecureString` CLIXML; only the Node child receives plaintext; the child environment is stripped of secret-shaped names; its output is line-redacted; stderr is discarded; failures print a stage name and line number only.

### 11.5 Installed-update qualification (verified, pass 2)

- A run is a private namespace under a fixed test bucket and origin: `dsh-desk/feeds/qualification/<id>/win-x64/nightly.yml` and a matching binary prefix, an application id `...qualification.q<id>` and a product name `DSH Update Test <id>`; `readInstalledUpdateRun` rejects any manifest whose identity fields, location or destinations changed.
- Upload and feed publication are separate operator actions with a lock directory. Binary upload first requires the bucket to report versioning disabled; every object is read (hashed) before and after the write; the feed is published only after a verified binary receipt, a re-verified package, and for the successor version only after journal evidence that the original app had started; the first feed refuses overwrite, the successor feed replaces the first. Each stage is recorded and a failure stops further writes.
- Package verification extracts the real installer payload and compares the ASAR contents, feed, cache name and publisher to the frozen inputs (`installed-update-package-content.ts`); builder execution requires a terminal and a typed confirmation and refuses to run while a signing interlock exists.

### 11.6 Runner operations (verified, pass 2)

- **Windows**: the setup script creates machine directories whose ACL allows only the current user, SYSTEM and Administrators (anything else is an error), refuses reparse points in any ancestor and non-fixed drives; the runner starts from a script that deletes every process environment variable outside a 27-name allowlist and optionally applies a validated proxy file and probes the network with a Node `HEAD` request before admitting the runner; the Task Scheduler installer registers a **disabled**, interactive, limited-rights task with priority 4, a persisted restart budget, a compiled no-console launcher, and a task description that encodes the runner path and owner so a task owned by something else is refused; `stop` refuses while a worker runs and kills only a process tree whose recorded pid and start time still match.
- **macOS**: the service script installs the runner's own LaunchAgent from a custom template, replaces the saved PATH with the Node 24 directory plus system paths, and starts the runner under `env -i` with an explicit variable list and `caffeinate -i`; the start script refuses anything but Apple Silicon and Node 24, checks that `notarytool`, `stapler` and the C toolchain work, and requires the test preset and the signing env file to exist.
- Both guides state that a login session is required after reboot and that no unattended boot is provided.

### 11.7 Installer and native helper (verified, pass 2)

- **Per-user only.** `customInit` exits with code 2 for an all-users run or an existing HKLM install; a `/THEME=` value outside light, dark, auto is an error; a silent run does the preflight and exits 2 on failure.
- **Path validation** (`path.nsh`): length 4 to 180, a fixed drive, none of `: * ? " < > | /` or control characters, no trailing dot or space in any segment, no Windows device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9`), no reparse point on the path or any existing ancestor, not the Windows or Program Files directories or beneath them, normalized through `GetFullPathNameW`; a new install needs an empty directory, an update needs the registered executable; free space must cover the unpacked size plus 64 MiB.
- **Directory transaction** (`installer-directories.nsh`): extract into `<dir>.new-<guid>`, rename the existing directory to `<dir>.old-<guid>` and the new one into place with `MoveFileExW`, retry only errors 5, 32 and 33 up to ten attempts with growing sleeps, restore on failure, remove the backup after promotion, and if restoration itself fails **stop recovery and keep the backup**, naming it in the report. `.onGUIEnd` cleans up unless recovery was stopped.
- **Extraction** (`extract.h`): the pinned 7-Zip runs inside a Job Object with kill-on-close and an explicit handle-inheritance list, stdout is a pipe parsed for percentage text, stderr goes to a log, exit codes are classified (7-Zip codes, negated Win32 errors, raw NTSTATUS in hex) and any non-zero code blocks promotion. Failure reports (`extract-report.h`, `directory-report.h`) are written as UTF-8 files and shown with a bounded excerpt and a copy button; silent installs write only the file.
- **Running-app check** matches the full image path (`QueryFullProcessImageName`), not just the file name; updates wait up to ten seconds (40 times 250 ms).
- **Progress is honest** (`progress.h`): stage boundaries 0, 2, 94, 96, 98, 99; extraction follows 7-Zip's percentage; the other stages use bounded exponential estimates; the bar reaches 100 only after the NSIS success callback, and a failure to create the progress window leaves the stock page visible.
- **Uninstall data removal** (`uninstall-data.h`, `uninstall.nsh`): a drive-absolute path on a fixed drive with no trailing dot or space; refuses a target that overlaps the installation directory or the configured Harness home in either direction (`DSH_HOME` when published as a Windows variable; an unusable value refuses), overlaps the native Program Files directory in either direction, equals or contains any of fourteen shell known folders, or (for Windows and both Program Files folders) lies inside them; opens every ancestor and the root as directory handles that deny delete sharing for the duration; removes by walking without entering reparse points (they are unlinked); attempts every sibling before returning the first error; skipped when the uninstall is part of an update or `/KEEP_APP_DATA` is passed. A failure leaves residue and never fails the uninstall.
- **Locales** (`installer-locales.mjs`): eight required locale files, each with `nsisLanguage`, 31 `INSTALLER_*` strings and an `uninstaller` dictionary of two strings; keys and format placeholder multisets must equal English; zero-width characters are rejected; generated NSIS strings escape `$`, quotes and line breaks.

## 12. Internationalization

## 13. Testing and performance

**Testing.** 181 `*.spec.ts` (about 1,291 cases), `*.e2e.ts` for real Electron, 59 golden files, 31 fixtures. Notable properties:
- **Behavior pinned at the composition root.** `main-startup.spec.ts` (2,990 lines, 100+ cases; about 250 lines read in pass 2) drives `main.ts` with substituted Electron and asserts: settings persistence and failure suspension, mandatory block semantics, hide-on-close, tray confirmation, macOS shutdown skip, quit-confirmation races, update dialogs and manual-check feedback, foreign-renderer IPC rejection, cleanup ordering before install. Titles are behavior statements ("accepts product IPC only from the current application top frame in the owned main window", "hides the workspace before intentional Host shutdown can look like reconnection").
- **Fake clocks, injected dependencies**: `DesktopUpdateSchedule`, `OperationJournal`, `DesktopFatalRecovery`, `runtime-tree` and `run-tree` accept injected time, random, spawn and filesystem operations; constructors validate budgets (`RangeError`).
- **Real-Electron fixtures**: loopback artifact server, real `NsisUpdater`, real sandboxed preload and mandatory renderer, 17 scenarios with screenshots; separate theme (12 cases) and overlay-visibility fixtures; an interactive Windows runner.
- **Installed-update qualification** is operator-driven and evidence-bound: a checklist, per-run journal, two synthetic versions, a firewall fault-injection script with typed confirmation, and a documented list of what the harness does *not* prove (no real installer, no differential updates, no macOS).
- **Honesty about evidence.** The README repeatedly separates "package succeeded" from "installed and qualified", marks unverified items (macOS login, enterprise code-integrity policy, notification qualification) and ties every claim to the layer that produced it.

**Performance techniques.**
- Parallelize independent startup work (login-shell read, profile preparation); show the loading document before the Host exists.
- `codeCache: true` on the custom scheme; `no-store` on per-launch plugin bundles; async system icons for drag.
- Bounded concurrency with drain-then-fail semantics (runtime hashing: 8; PE header reads: 8 open files; signature checks: batches of 32, at most 4 processes; cache restore 4 default, 1..8; tarball packing 4 default); overlapping tarball packing with Electron and runtime preparation in separate output directories; LZMA (`ULMO`) DMG.
- Hard budgets everywhere: 64 MiB drag stage, 64 KiB journal queue, 4 KiB record, 256 KiB segment, 256 KiB error section, 1,200-character dialog detail, 500 ms shutdown drains, 2 s quit inspection, 10 s control requests, 60 s update idle.
- Native installer progress uses one reused pixel buffer and copies repainted regions only; repaint timings are diagnostics, not CI limits.
- Windows packaging CI normalizes process CPU/I/O/memory priority and refuses to treat a run with unavailable priority control as a performance comparison.

**Additional findings (verified, pass 2).** What the spec files I read actually pin:
- `update-coordinator.spec.ts`: approval needs the exact version (a stale string rejects), 100 percent progress is not readiness, an asynchronous installer error after `quitAndInstall` is retained, late updater errors after disposal are consumed so they cannot throw, checks and downloads join, a failed task preparation keeps the prepared package, channel switching retires a downloaded target and rejects its old confirmation, and old, equal or malformed versions never reach download or install on either channel.
- `update-schedule.spec.ts`: delay doubles to the cap, jitter samples are bounded so the final delay never exceeds the cap, the delay starts at completion, wall-clock jumps are ignored (monotonic timer), policy arrival bypasses the automatic deadline silently, and nothing downloads automatically.
- `mandatory-update-policy.spec.ts`: a known block survives expired login, 422 and HTTP 500 bodies that look like success; HTML and unrelated 401s are not treated as login; anonymous mode never enables login; headers carry platform, version, locale, timezone, arch, channel and bundled version, sampled per check; a channel change waits for the old request then checks the new channel; `dispose` aborts and awaits and suppresses late publishes; configuration rejects unsafe origins and out-of-range numbers.
- `windows-timestamp.spec.ts` and `windows-sign.spec.ts`: a failed timestamp cannot contaminate the next attempt or repeat hardware signing; exhausted attempts keep evidence and leave the input unchanged; unretryable process failures (`ENOENT`, killed, signal) do not retry; a valid signature with changed content is rejected; an input changed during completion is not overwritten; deep paths use short private paths; a PIN failure rejects the queue and keeps the interlock; `fatal.json` exists on every failure mode; the PIN never appears in records.
- `web-document.spec.ts`: traversal (`%2e%2e%2f`) returns 403, missing assets 404, a foreign `Origin` is refused without forwarding, the Host cookie is attached and `set-cookie` removed, immutable cache headers on plugin bundles become `no-store`, and only legacy auth cookies are removed.
- `main-startup.spec.ts` (selected): product IPC from any sender other than the owned main frame throws "unowned renderer" for status, channel and device channels; WebSocket header rewriting applies only to the owned window and Host authority and cancels a foreign `Origin`; `updateTasks` call sequences for dismissal, approval, new work and drain failure; restoring a Host after a clean stop or an unclean exit, with and without a mandatory block; a Host whose failed stop is unconfirmed is never replaced.
- `tests/expected/`: the COS access-denied case is a golden JSON with operation, code, request id and HTTP status; `windows-installer.json` lists 16 installer scenarios (including "locked directory shows error and preserves installation" and "running app rejected before welcome and extraction"); `windows-uninstall.json` lists five uninstall scenarios.

## 14. Recommendation summary and proposed tasks

Adopt, adapt, reject at a glance (packages touched in brackets).

**Reject:** loopback HTTP Host with cookie and custom-scheme proxy (LiteCowork uses pipe/UDS); in-process plugins; `runAsNode`; mandatory-update policy service, Feishu auth, analytics, Platform embedded account views; macOS vibrancy and notarization work (not in V1); native GDI+ installer renderer; COS/EdgeOne publishing; bundled Python/Node/pnpm runtimes (for V1); `dsh` PATH command installation and its ownership receipts (LiteCowork has no V1 CLI; the fingerprint-bound confirmation, backup-and-restore and "foreign entry is never removed" rules read in `command-installation.ts` are a good reference if a CLI shim is ever added, and the fingerprint idea is already covered by 013-T08 approvals); the macOS system-proxy transaction for notarization; the test-login policy window and its Feishu flow; the `WineVmManager.exec` patch that signs the NSIS bootstrap (prefer a documented sign hook).

**Conflict note: login-shell environment vs environment scrubbing.** `login-shell-environment.ts` runs the user's login shell (from the user database, not `$SHELL`) as `-ilc`, reads `env -0` between delimiters under a process-group-killed 10 s timeout, falls back through `zsh`, `bash`, `sh`, ignores `PWD`, `OLDPWD`, `SHLVL`, `_`, and launcher-owned names, and merges the result *over* the inherited environment for the Host and everything it spawns. Pass 2 read the whole file: candidates are the account record's shell then `/bin/zsh`, `/bin/bash`, `/bin/sh`; each has a 10 s deadline (`DSH_DESKTOP_LOGIN_SHELL_TIMEOUT_MS`, validated 1 s to 2^31-1 ms), a closed stdin, its own process group (killed whole on timeout or abort), and a probe environment that disables oh-my-zsh updates and tmux autostart; the read ends at the closing delimiter because background children started by rc files can hold stdout open; names starting `DSH_` or `ELECTRON_` and session variables are never overwritten; Windows returns the inherited environment unchanged; the function never rejects and returns the failed candidates for diagnostics. This fixes "GUI launch misses PATH", which will bite LiteCowork on Linux when a native agent such as OpenCode or Claude Code is launched from a desktop entry. But it conflicts with LiteCowork's rule that captured subprocesses receive a scrubbed environment (compare `scrubbedParentEnv` in A-58) and with 005 Environment boundaries. Resolution proposed: capture the login environment once in the shell/daemon, store only a **PATH-class allowlist** (PATH, locale, XDG dirs, toolchain homes), and never forward credentials from it. That needs an owner decision (it is the single place where this study asks to loosen a LiteCowork default), so it is a proposal, not a recommendation to merge.

## 15. What remains unread, and what not to conclude

Read depth is in Section 0. In short: `src/` about 87% line by line, `scripts/` about 58%, `installer/` text about 75%, English guides about 100%, tests about 5%. What this means for the proposals above:

- **`scripts/` (about 6,400 lines unread).** The runtime preparation and smoke sources (`prepare-*.ts`, `smoke-runtime.ts`, `smoke-packaged-runtime.ts`, `smoke-prepared-runtime.ts`) were not read, so P-35's description of what the packaged smoke asserts, and how it keeps a private data root private, rests on the README and file headers. Read these before P-35 becomes a design. `windows-token-public-key.cs` (the CSP reader behind the token identity check), `publish-website-ci.ts` and `desktop-release-tag.ts` were also not read.
- **Tests (about 95% unread).** Only the update coordinator, schedule, mandatory policy, timestamp, signing-state, web-document, part of `windows-sign` and about 250 lines of `main-startup` specs were read. Before P-31 and P-34 become specs, read `host-process.spec.ts`, `host-update-tasks.spec.ts`, `update-dialog.spec.ts`, `update-discard.spec.ts`, `update-http-executor.spec.ts`, `fatal-recovery.spec.ts`, `operation-journal.spec.ts` and the remaining 2,700 lines of `main-startup.spec.ts`. The 1,291-case figure is a pattern count; case behavior outside the files named in Section 13 is inferred from titles only.
- **Wording.** The eight `locale.ts` catalogs and the eight installer locale JSON files were checked for structure, not read for meaning. Any translation quoted here is from `tests/expected` heads or the English catalog's first lines.
- **Installer UI.** `pages.nsh` 141 to 386, `extract-report.h` 121 to 331 and the tail of `window-frame.cpp` (layout, dialog and error text) are unread; the safety and transaction logic that matters for P-41 was read.
- **Dependencies.** `electron-updater` 6.x internals that `discard.ts` edits, `app-builder-lib` templates that `windows-directory-installer.mjs` patches, `@electron/notarize`, `cos-nodejs-sdk-v5` and the workspace packages this app imports (atomic write, plugin-manager diagnostics, file-drag utilities, shortcut protocol) were not read; only their names and call sites appear here.
- **Mirrors and assets.** The ZH guide mirrors and `README.i18n.yaml` files, `renderer/` CSS and scripts, `resources/` and the config examples beyond one sample.

What not to conclude:

- This study does not show that DeepSeek's update, signing or installer flows are correct on real machines. Its own guides list unqualified items (macOS login, enterprise code-integrity policy, notification behavior, differential updates, installed macOS flow, real COS/CDN permissions, token PIN retry counts), and the Windows signing guide records accepted isolation risks (shared runner account, same-account cache trust). The signing throughput numbers are one host with one token.
- Reading is not running. No code or test from the clone was executed; "the spec pins X" means the assertion exists in the spec text I read.
- The sealed-inventory, signing and publication designs are patterns. LiteCowork's choices of Tauri, MSI or NSIS, signing service and distribution endpoint are undecided in the documents this study touched; each adoption above names the package and task that must make that decision.
- Licenses must be re-checked at the repository root before any code is adapted; this document adapts no code and copies none. The clone stays gitignored.
